# Перенос домена на VPS: механика, DNS-менеджмент, выбор регистратора
_Дата: 04.09.2026. Только подтверждённые данные; источники указаны в тексте._

---

## 1. Главный принцип: «перенос» ≠ «трансфер»

Сайт на VPS работает **без смены регистратора**. Достаточно управления DNS у текущего:

| Действие | Что меняется | Скорость |
|---|---|---|
| **A-запись** (@ и www → IP VPS) | записи у текущего DNS | минуты–часы, ограничено старым TTL |
| **Делегирование на другие NS** (в т.ч. российские DNS-сервисы) | NS-записи у регистратора | до 24–72 ч |
| **Трансфер к другому регистратору** | смена регистратора | до 5 календарных дней (ICANN) |

Трансфер — отдельная, самая медленная операция, и для привязки к VPS он **не требуется**.

## 2. Точные шаги привязки домена к VPS (A-запись)

1. **Аудит (день 0):** `whois домен` — узнать регистратора и текущие NS; `dig NS домен` и `dig A домен` — зафиксировать текущий TTL.
2. **За 24–48 ч до смены IP:** снизить TTL до **300–600 сек** для A-записей (@, www). Это стандартная рекомендация — скорость обновления после смены IP определяется **старым** TTL, не новым (источники: exit1.dev/blog/dns-propagation-how-long-do-changes-take; ruvds.com/ru/helpcenter/kak_privyazat_domen_k_vps).
3. **Смена:** в панели регистратора/DNS-провайдера создать/изменить:
   - `@ A <IP_VPS>` (для сценария 201.3.225.93-like — просто IPv4 датацентра)
   - `www A <IP_VPS>` или `CNAME www → корень`
   - MX/SPF/DKIM не трогать, если почта остаётся на прежнем сервисе.
4. **Проверка:** `dig +short @1.1.1.1 домен`, `dig +short @8.8.8.8 домен`, dnschecker.org — пока старый TTL не истёк, часть резолверов вернёт старый IP; это нормально.
5. **После подтверждения:** поднять TTL обратно до **3600** (стандарт для стабильных записей; BIND на собственном NS VPS обычно настраивают с TTL 3600 — ruvds).
6. **(Опционально) собственный NS на VPS:** поднять BIND/PowerDNS, прописать у регистратора `ns1/ns2.<домен> → A <IP_VPS>` (клей-записи). Работает, но добавляет единую точку отказа — для одного VPS обычно избыточно.

Ориентиры распространения: A-записи — минуты–часы (реально ≈ старый TTL); смена NS/делегирование — до 24–72 ч (Yandex Cloud docs, cloud4box). Формальные «48 часов» — худший случай, при TTL 300 обновление занимает ~5–10 минут.

## 3. Трансфер к другому регистратору (если нужен)

Правила ICANN (icann.org/resources/pages/name-holder-faqs-2017-10-10-en; FOA-шаблон 2024):
- **Auth-code (EPP)** обязателен; запрашивается у текущего регистратора.
- **60-дневный лок** после первичной регистрации, после завершённого трансфера и (часто, опционально у регистратора) после смены регистранта (COR) — трансфер в эти окна отклонят.
- После подтверждения FOA трансфер завершается **в течение 5 календарных дней**, если текущий регистратор его не отклонил; бездействие = авто-одобрение.
- Практика: DNS-зона при трансфере обычно переносится копией, поэтому сервис не прерывается — но скопируйте все записи вручную до старта.

## 4. Crypto-регистраторы: кто наименее проблемный

| Регистратор | Крипта | Модель владения | Custom NS | Примечание |
|---|---|---|---|---|
| **NameSilo** | BTC; через интеграцию Nicky (03.2025) BTC/ETH/LTC/USDT/USDC | домен на ваше имя | да, без ограничений | бесплатный полноценный DNS-менеджер; самый «обычный» из крипто-вариантов (namesilo.com/payment-options/bitcoin; accessnewswire) |
| **Njalla** | BTC (вкл. Lightning), LTC, **XMR**, ETH, PayPal | **прокси-владение: домен оформлен на Njalla** | да, «Use custom nameservers» (docs.sutty.nl) | без KYC; риск: жалобы на блокировки аккаунтов и трудности с получением auth-code при уходе (Trustpilot) |
| Dynadot, Porkbun | крипта (по обзорам 2026) | обычная | да | из обзоров idahocitychamber/monstadomains — вторичное подтверждение |
| OrangeWebsite, 1984 Hosting | крипта, no-KYC | обычная/локальная | да | нишевые, Исландия (monstadomains.com) |

**Рекомендация для связки с VPS:** NameSilo как баланс (крипта + вы юридический владелец + свободные custom NS). Njalla — максимальная приватность, но принимайте модель прокси-владения и риск при выводе домена.

## 5. Crypto-регистратор + российские DNS-сервисы: работает ли

**Да, работает без ограничений.** Механика:
- Делегирование — это просто NS-записи у регистратора; DNS-инфраструктура не зависит от юрисдикции регистратора.
- Подтверждённый кейс (Yandex Cloud docs, tutorials/infrastructure-management/connect-migration): у стороннего регистратора прописываются NS `ns1.yandexcloud.net` / `ns2.yandexcloud.net` (или NS Яндекс 360), публичная зона создаётся у Яндекса, A-записи ведутся там. Распространение — до 72 ч. Аналогично для reg.ru DNS и DDoS-Guard: любой регистратор с полем «custom nameservers» их примет.
- У Njalla: Domains → Manage → «Use custom nameservers» → вписать российские NS. У NameSilo: Account → Domain Manager → NameServers → custom.
- Санкционных ограничений на DNS-записи (A/NS/MX) между «западным» регистратором и российским DNS-хостингом нет — ограничения касаются услуг, а не записей DNS.

## 6. Риски

1. **Прецедент отключения сервисов:** Namecheap в марте 2022 прекратил хостинг/почту для клиентов, зарегистрированных в РФ, с требованием перенести домены к 22 марта; доменные операции сохранялись по ICANN-аккредитации (theverge.com; gazeta.ru; namecheap.com FAQ). Вывод: **разносите регистратора, DNS и хостинг по разным провайдерам** — тогда любой элемент заменяется независимо.
2. **60-дневные локи ICANN** — планируйте трансфер заранее, не меняйте регистранта перед ним.
3. **Njalla:** домен юридически не ваш; при споре/блокировке аккаунта вывод осложнён (Trustpilot-жалобы, ICANN-жалобы пользователей).
4. **TTL-ловушка:** скорость обновления = старый TTL. Всегда снижайте TTL до правки, а не после.
5. **Единый NS на VPS:** BIND на самом VPS — точка отказа; лучше DNS-панель регистратора или облачный DNS (Яндекс Cloud / Cloudflare / NameSilo DNS).
6. **Почта:** при смене только A-записей MX не трогаются; при смене NS — переносите MX/SPF/DKIM/DMARC первыми, иначе почта ляжет раньше сайта.

## 7. Итоговый план (универсальный)

1. TTL → 300 за сутки-двое до работ.
2. A-записи @/www → IP VPS; проверка через dig/чекеры; TTL → 3600.
3. (Опц.) делегирование на выбранный DNS-сервис (в т.ч. российский) через custom NS у регистратора.
4. (Опц., заранее, без локов) трансфер к NameSilo/Njalla за auth-code, до 5 дней.
5. Почтовые записи переносить до смены NS; сайт проверять по IP напрямую (`curl -H "Host: домен" http://<IP>`) до распространения DNS.
