## 3. Целевая hybrid-архитектура

Каноническая папка выбирается как **основа продукта**, а не как утверждение, что её текущая архитектура уже финальна.

Целевые роли компонентов:

1. **Telegram Mini App / PWA** — UI, offline cache, локальная очередь операций и быстрый доступ к safety-информации.
2. **Backend API** — серверное хранение, синхронизация, Telegram-аутентификация, multi-device, аналитика и необходимые серверные safety-сценарии.
3. **Telegram Bot** — обязательная точка входа, запуск Mini App, уведомления, напоминания и разрешённые серверные сценарии эскалации.
4. **IndexedDB** — не единственный источник данных, а локальный cache/outbox для offline-first UX.
5. **Server database** — долговременный авторитетный слой синхронизируемых пользовательских данных; точные правила конфликтов и шифрования должны быть оформлены отдельным ADR.

Backend не следует механически копировать внутрь frontend-папки. Сначала требуется определить API-контракт, модель синхронизации, владение данными, конфликт-резолюцию и privacy boundaries.

## 5. Правила дальнейшей работы

1. Новые продуктовые изменения выполняются в `USNEE v2\usnee`.
2. До любых крупных правок необходимо сохранить или отдельно зафиксировать существующий dirty state.
3. Из DONOR-каталогов не копируются целые деревья. Для каждого переноса оформляются:
   - источник;
   - назначение;
   - diff;
   - адаптация к текущим типам/API;
   - тесты;
   - результат build/typecheck.
4. REFERENCE-файлы не считаются доказательством реализованной функциональности.
5. ARCHIVE-каталоги не редактируются и не удаляются в рамках P1.
6. Секреты из `.env` не копируются между версиями и не коммитятся.
7. Сгенерированные `dist`, `node_modules`, `.venv`, IDE и agent-служебные файлы не должны становиться источником кода.
8. Утверждённое visual direction переносится в код через design tokens и компонентный слой, а не прямым копированием статического HTML.

## 6. Текущий продуктовый приоритет

Зафиксирован следующий рабочий срез:

1. **Стабильная запись инъекций** — Quick Record как основной путь и Add Entry как расширенная форма.
2. **History** — чтение, честный статус синхронизации, просмотр, безопасное редактирование и компенсирующее удаление.
3. **Базовая Stats** — нейтральные агрегаты количества записей по дням и веществам без суммирования несовместимых единиц.

Safety Hub отложен. Существующего честного SOS-sheet достаточно для текущего этапа; полное выравнивание `Safety.tsx` не блокирует основной функционал.

### Границы текущего среза

- запись сначала атомарно сохраняется локально и помещается в outbox;
- интерфейс не выдаёт локальное сохранение за подтверждённую серверную синхронизацию;
- для инъекций обязательны положительный объём и выбранное вещество;
- Quick Record не удаляет широкую расширенную форму;
- History не выполняет физическое удаление новых записей, а создаёт компенсирующую операцию;
- legacy-записи без sync metadata не удаляются до появления безопасной миграции;
- Stats не складывает мл, мг, г, таблетки и другие несовместимые единицы в одну «общую дозу»;
- backend transport, bot и обработка outbox на сервере остаются следующей интеграционной стадией.

### Ближайший порядок работ

1. Проверить и стабилизировать локальную транзакцию `entry + outbox + sync metadata + batch movement`.
2. Проверить Quick Record, duplicate guard, undo и обязательные поля инъекции.
3. Проверить расширенный Add Entry на том же persistence path.
4. Проверить History: сортировка, статусы, detail, edit и compensating delete.
5. Проверить базовые Stats на реальных локальных записях и смешанных единицах.
6. Добавить/обновить unit и component tests, затем выполнить typecheck, test run и production build.
7. Только после стабильного локального среза подключать серверный outbox transport и Telegram-authenticated API.

## 7. Не решено этим документом

- структура mono-repo или нескольких репозиториев;
- конкретная backend-папка внутри будущей структуры;
- API schema и sync protocol;
- правила end-to-end encryption;
- основной показатель партии: масса, объём раствора или оба;
- финальный логотип;
- production hosting;
- медицинская и юридическая верификация safety-контента.

До фиксации этих решений текущие реализации в DONOR/REFERENCE не должны автоматически считаться финальными.
